## 1. 事实来源

按以下优先级判断事实：

1. 仓库中的真实代码和数据；
2. 可重复的检查结果和实际运行行为；
3. Git 历史；
4. 已批准的仓库文档；
5. Agent 报告和聊天记录。

把聊天视为临时上下文，不作为项目唯一记忆。代码与文档不一致时，先验证真实代码，报告文档偏差，只在授权范围内同步文档。

## 2. 角色边界

### 项目所有者

- 决定产品目标、优先级、视觉方向和非目标。
- 批准 Product Brief、重大技术方向、主分支合并和生产部署。
- 授予或撤销 Codex 的 Git/GitHub push 权限。
- 为破坏性或不可逆操作提供单独授权。

### GPT 产品规划者

- 把 Idea 整理成产品选项、范围、非目标、优先级和验收标准。
- 生成 Product Brief，交给项目所有者批准。
- 不决定文件级实现、框架、依赖或数据模型。

### Codex 技术负责人

- 在项目接入、里程碑变化或高风险任务时检查仓库。
- 规划已选里程碑和 Major 任务。
- 定义边界、依赖、检查、风险和回滚。
- 只在批准的触发条件成立时审查。
- 验证后 push 任务分支，并创建或更新 GitHub PR。
- 默认不编码；项目所有者明确授权后，Codex 才在该任务中切换为编码角色。

### TRAE 编码 Agent

- 阅读任务范围、相关代码、测试和 Git 状态。
- 实现最小而完整的改动。
- 增加或更新检查，报告准确结果。
- 创建本地任务提交。
- 默认不扩大产品范围、不改架构、不 push、不合并、不部署。

### TRAE 审查 Agent

- 使用独立上下文。
- 审查固定 commit 或明确记录的 diff。
- 复现关键检查，检查范围、回归和可维护性。
- 担任审查者时不修改源码。
- 如果转为编码角色，修改结果必须交给另一个独立审查 Agent。

## 3. Codex 额度规则

把 Codex 额度集中在：

- 第一次可信项目基线；
- 已选里程碑规划；
- Major 任务；
- 里程碑关闭；
- 架构、公共 API、核心数据、依赖、安全、隐私或部署变化；
- 审查冲突；
- 无法解释的测试或构建失败；
- 范围偏离；
- 项目所有者明确要求。

Quick 任务默认跳过 Codex。Standard 任务复用已批准计划，由 TRAE 实现、独立审查并运行自动检查。

把相关 Standard 任务合并为一次里程碑验收。不要要求 Codex 重读未变化模块或完整聊天。

交给 Codex 前准备最小证据包：

```text
已批准的产品依据或任务来源
Technical Plan 引用
git diff --stat
修改文件列表
Review Status 和阻断问题
准确的检查命令和结果
需要 Codex 判断的具体问题
```

只有证据指出具体风险时才扩大上下文。

## 4. 任务分级

### Quick

必须同时满足：

- 风险低、容易回滚；
- 局部范围清楚；
- 不改变产品行为或公共 API；
- 不涉及 schema、依赖、权限、敏感数据、部署或迁移。

适用于文档、文案、小范围视觉调整和边界明确的局部修复。

### Standard

适用于已被批准技术方向覆盖的普通功能、行为变化和跨文件修复。

要求：

- 独立任务分支或 worktree；
- 同一时间只有一个源码写入 Agent；
- TRAE 独立审查；
- 运行真实项目检查；
- 项目所有者决定是否合并。

### Major

适用于：

- 架构或核心数据模型变化；
- 迁移、删除或不可逆操作；
- 安全、隐私、权限或账户；
- 部署平台或基础设施变化；
- 核心依赖变化；
- 大规模重构；
- 强耦合跨项目集成。

要求 Codex Technical Plan、实施前所有者批准、回滚和数据保护、扩展审查、Codex 针对性验收以及部署前验收。

任何 Agent 都可以升级任务等级。只有 Codex 或项目所有者可以批准降级。

## 5. 规划与执行关卡

使用适用的状态流：

```text
DRAFT
→ PRODUCT_APPROVED（需要产品审批时）
→ TECHNICALLY_PLANNED
→ IMPLEMENTED
→ REVIEW_PASSED
→ CODEX_ACCEPTED（触发 Codex 时）
→ OWNER_APPROVED
→ MERGED
→ DEPLOYED
```

纯技术任务可以省略 `PRODUCT_APPROVED`。未触发 Codex 的 Standard 任务可以省略 `CODEX_ACCEPTED`。不得跳过当前等级要求的关卡。

Standard 执行流：

```text
已批准产品依据（需要时）
→ 现有 Codex 里程碑计划
→ TRAE 紧凑任务卡
→ 编码 Agent
→ 独立审查 Agent
→ 原编码 Agent 修复问题
→ 自动检查
→ 触发时交给 Codex
→ Codex push 任务分支并创建 PR
→ 项目所有者决定是否合并
```

同一 worktree 同一时间只能有一个源码写入 Agent。允许不同 Agent 串行接力，但必须：

1. 前一个 Agent 停止编辑；
2. 固定 commit 或记录完整 diff；
3. 记录检查和 Git 状态；
4. 新 Agent 从仓库证据重新建立理解。

## 6. Git、GitHub 和 worktree

- Quick 任务可以使用干净的当前分支。
- Standard 和 Major 任务使用独立分支或 worktree。
- worktree 属于代码状态，不永久属于某个 Agent。
- TRAE 可以创建本地任务提交，默认不得 push。
- Codex 可以 push 任务分支并创建或更新 PR。
- push 前检查分支、commit、验证结果、远程目标和敏感信息。
- 项目所有者批准主分支合并和生产部署。
- 强制 push、远程历史改写和远程分支删除需要单独授权。
- 不清理、重置或覆盖无关用户改动。

## 7. 交接与报告

报告长度与风险相称。

### Quick

只使用五个字段：

```text
Changed
Files
Checks
Risk
Git
```

除非风险升级，否则不创建持久任务文档。

### Standard

字段保持简短。引用已有计划、commit 和检查日志，不重复粘贴。

包括：

- 紧凑任务卡；
- 紧凑实现报告；
- 独立 Review Report；
- 仅在触发时记录 Codex escalation；
- Owner Decision。

Review Status 只允许：

```text
APPROVED
CHANGES_REQUESTED
REJECTED
```

没有问题或风险时写 `None`。

### Major

按需使用完整 Product Brief、Technical Plan、Rollback Plan、Implementation Report、Review Report、Codex Acceptance 和 Owner Decision。

## 8. 验证与完成

只运行仓库真实存在的命令。不得编造 `npm test`、`pytest` 或其他检查。

编码 Agent：

- 建立相关基线；
- 先运行针对性检查；
- 再运行任务要求的较完整检查；
- 记录准确命令、结果和既有失败。

审查 Agent：

- 阅读真实 diff；
- 复现关键检查；
- 检查边界、回归、失败路径和可维护性。

Codex 触发后：

- 先读取最小证据包；
- 检查风险相关 diff 和模块；
- 只复现决策关键检查；
- 记录剩余风险和 Git/GitHub 状态。

不得删除测试、扩大 skip、降低断言或隐藏失败来制造通过。

任务完成必须满足：

- 实现符合批准结果；
- 范围可以解释；
- 必要检查通过；
- 阻断审查问题已解决；
- 必要文档已同步；
- 触发的 Codex 验收通过；
- 项目所有者接受产品结果；
- push、PR、合并和部署状态明确。

`IMPLEMENTED`、已提交、已 push、已合并和已部署是不同状态。

## 9. 失败与升级

遇到以下情况立即停止：

- 可能丢失、覆盖或泄露用户数据；
- 安全或隐私暴露；
- Git 历史损坏；
- 生产环境中断；
- 仓库状态与计划冲突；
- 必须扩大范围才能继续；
- 同一失败经过两次实质相似尝试仍未解决。

报告：

```text
失败步骤
命令或操作
预期结果
实际结果
严重程度
已尝试方法
当前修改文件
检查或构建状态
Git 状态
最安全下一步
```

未经项目所有者单独授权，不执行：

```text
git reset --hard
git clean -fd
git push --force
远程历史改写
远程分支删除
用户数据删除或覆盖
生产迁移或部署
```

代码问题退回编码 Agent，计划偏离交给 Codex，产品歧义退回 GPT 和项目所有者，重大方向失败重新设计。

凭据、token、个人数据和支付信息不得进入 prompt、报告、asset、commit、日志或前端字段。

## 10. 项目后续升级

以下情况触发升级审查：

- 项目所有者提出新方向；
- 里程碑关闭；
- 用户反馈要求变化；
- 技术债阻塞开发或测试；
- 安全、依赖、平台或部署条件要求变化。

使用：

```text
TRAE 整理当前证据
→ GPT 提供产品升级选项
→ 项目所有者选择方向
→ Codex 只分析已选方向的技术影响、顺序、风险和回滚
→ 更新适用的 ROADMAP / DECISIONS / ARCHITECTURE
→ 按任务等级执行
→ 关闭里程碑
```

不要消耗 Codex 额度深入分析尚未被项目所有者选择的方案。

## 11. 权限矩阵

| 操作 | 项目所有者 | GPT | Codex | TRAE 编码 | TRAE 审查 |
|---|---|---|---|---|---|
| 决定产品目标 | 最终决定 | 提案 | 建议 | 否 | 否 |
| 批准 Product Brief | 是 | 否 | 否 | 否 | 否 |
| 设计技术方向 | 可参与 | 否 | 主要负责 | 可建议 | 可审查 |
| 判断争议或高风险任务 | 可覆盖 | 否 | 主要负责 | 可升级 | 可升级 |
| 修改源码 | 可 | 否 | 明确编码授权后 | 是 | 否 |
| 创建本地任务提交 | 可 | 否 | 编码时 | 是 | 否 |
| 独立代码审查 | 可 | 否 | 触发验收 | 否 | 主要负责 |
| push 任务分支 | 可撤销权限 | 否 | 是 | 默认否 | 否 |
| 创建或更新 PR | 可撤销权限 | 否 | 是 | 否 | 否 |
| 合并主分支 | 最终批准 | 否 | 批准后执行 | 否 | 否 |
| 生产部署 | 最终批准 | 否 | 批准后执行 | 否 | 否 |
| 删除用户数据 | 明确批准 | 否 | 默认禁止 | 禁止 | 禁止 |

项目规则更严格时，遵循更严格的规则。
